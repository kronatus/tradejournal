# Keep Tradier serving quotes, add Robinhood alongside

Robinhood MCP now returns everything the journal needs from a quote — **delta, gamma, theta, vega, rho and implied volatility, inline on every option quote object, in a single call** — and that was verified empirically in this session, not inferred from marketing. Yet the answer to "can we switch the Tradier lookup?" splits cleanly in two. For proposition (a), replacing Tradier in the deployed web app's server-side quote path, the answer is **no**, and the blockers are not data quality but plumbing: Robinhood addresses contracts by opaque instrument UUIDs that no OCC symbol can be converted into, it returns an **empty array rather than an error** when handed an identifier it does not recognise, its OAuth uses **rotating refresh tokens** that a serverless platform's concurrent invocations will actively destroy, and the token it issues grants read access to the user's entire Robinhood financial picture rather than to quotes alone. For proposition (b), using Robinhood MCP interactively from Claude and as an additive source for positions, order history and realized P&L, the answer is **yes, and it is the genuinely valuable half of the question** — that data does not exist in Tradier at all, and the journal's own architecture analysis shows unrealized P&L and per-leg marks are precisely what the app currently cannot compute. The recommendation is therefore not "Robinhood or Tradier" but "Tradier stays in the hot path; Robinhood becomes a reconciliation and exploration surface, reached from Claude rather than from Vercel."

## The decisive fact is settled: Greeks and IV ship with every option quote

The single question that gated this whole evaluation — does `get_option_quotes` carry Greeks, or only price — was answered by direct calls against the live server on 2026-09-19. It does. A two-contract call on SPY 2026-10-16 returned, per contract, the field names `implied_volatility`, `delta`, `gamma`, `rho`, `theta` and `vega`, alongside `bid_price`/`ask_price`/`mark_price`, `open_interest`, `volume`, and Robinhood-specific `chance_of_profit_long`/`chance_of_profit_short`. The ATM $760 call reported `delta` `0.563302`, `theta` `-0.243408`, `vega` `0.828369` and `implied_volatility` `0.133142`. This matches Robinhood's own claim that agents can "pull quotes with full Greeks" ([@RobinhoodApp](https://x.com/RobinhoodApp/status/2065441614659482094)), and it contradicts the tool's own `guide` text, which discusses only price and close handling and never mentions Greeks at all. The documentation undersells the payload.

Three structural properties of that payload matter for this codebase. **Every money value and every Greek arrives as a decimal string**, not a number — which is a quiet gift to a project whose convention is integer cents and never floats, since a string parses to cents without ever passing through a float. **Greeks are not conditional on liquidity**: a follow-up batch of 25 contracts carried complete Greeks on every one, including zero-volume, zero-open-interest deep-ITM strikes. And **the 20-contract cap is softer than the schema implies** — a 25-id call returned 25 full quote objects and dropped only the official `close` sub-object, flagging the degradation with an explicit `closes_error`. For a personal journal whose largest strategy is a handful of legs, batching is a non-issue.

Two caveats travel with the good news. Option quotes carry **no `last_trade_price` field at all** — a marked contrast with `get_equity_quotes`, which returns both `last_trade_price` and `last_non_reg_trade_price`. Any Robinhood-sourced pricing is mark-based. Today `lib/quotes.ts:103` normalizes as `price = q.last ?? (q.bid + q.ask) / 2`, so a switch would silently collapse to the midpoint branch for every contract — arguably more correct on illiquid strikes, but a behavioral change, not a null one. Second, **outside regular trading hours the quotes are a frozen prior-session snapshot with no market-state flag to tell you so**. The probe ran roughly 28 hours after the data was captured: all 25 contracts carried `updated_at` clustered in `2026-09-18T20:14:57Z`–`20:14:59Z`, just after the prior US close. Equity quotes expose `state` and `has_traded`; option quotes expose neither. Staleness is detectable only by reading `updated_at` yourself, which the tool's guide explicitly instructs callers to do. **In-hours latency was never tested** — the session ran while the market was closed — so whether `updated_at` tracks within seconds during RTH remains unverified.

## UUID addressing would add a third symbol format to the project's worst bug area

Robinhood's option tools are keyed by instrument UUIDs, and there is no OCC lookup path anywhere on the surface. Passing the perfectly well-formed OCC symbol `"SPY261016C00660000"` to `get_option_quotes` returned `{"data":{"results":[],"closes_error":"..."}}` — an **empty result set with no error naming the bad identifier**. That is the most dangerous single finding in the entire investigation, and it is dangerous specifically because of what this codebase already is. `OCC_SYMBOLOGY.md` opens by calling the strike encoding "the #1 Source of Bugs" and documents three historical failures from the Tradier migration alone. The first of those — sending a cents-encoded strike where dollars×1000 was expected — was *caught* because Tradier answers a bad symbol with `unmatched_symbols`. Robinhood answers with silence. The same class of mistake that Tradier surfaces as a visible error would, through Robinhood, surface as a quote that simply never arrives, aggregated into net Greeks that are quietly short a leg.

The concrete shape of the migration cost is a resolution chain. Reaching a price for "SPY, 2026-10-16, $660 call" took `get_option_chains(underlying_symbol="SPY")` to obtain the chain UUID `c277b118-...` and its 32 expiration dates, then `get_option_instruments(chain_id, expiration_dates, strike_price="660.0000", type="call")` to obtain the instrument UUID `73500909-...` — a call which returns **no prices and no Greeks** — and only then `get_option_quotes`. Three round trips cold, two if the chain UUID is cached, against Tradier's one. The saving grace is fan-out: pricing N contracts on one expiration is still roughly three calls, not 3N, and UUIDs are stable per contract, so a persisted OCC→UUID mapping table would reduce steady-state refresh to a single quote call. But that mapping table is **mandatory, not optional**, and it means introducing a third identifier space into a project that already juggles two (`O:SPY260529C00075500` in storage, `SPY260529C00755000` for Tradier) and where the existing architecture analysis found that `components/strategy-form.tsx:54` has already reimplemented `buildOccSymbol` with divergent semantics from the canonical `lib/quotes.ts:51`. That analysis also recorded that **`lib/quotes.ts` and `lib/snapshots.ts` have zero test coverage** — the conversion boundary `nextsteps.md:48` calls "the highest-risk integration boundary" is entirely unguarded. Adding a silent-failure identifier space on top of an untested conversion layer, in the area the project itself names as its worst, is the definition of a bad trade.

The mitigation, if anyone ever attempts this, is simple and should be written down now: **assert `results.length === instrument_ids.length` and treat any shortfall as a hard error**, because the API will not raise one for you.

## Rotating refresh tokens fight Vercel's execution model in a way a static token never does

The current design is one static `TRADIER_API_TOKEN` env var, server-side only, feeding a single batched `GET` per Refresh click. Robinhood has no equivalent. Authentication is OAuth 2.1 with PKCE S256 against `https://api.robinhood.com/oauth2/token/`, registered as a **public client** (`token_endpoint_auth_methods_supported: ["none"]`), returning an access token with `expires_in: 344000` — about four days ([claude-code issue #65895](https://github.com/anthropics/claude-code/issues/65895)). The access-token lifetime is not the problem. The refresh chain is: **Robinhood rotates refresh tokens on every use, each refresh returning a new one and instantly invalidating the old** ([SecProve](https://secprove.com/trading-agent-safety/robinhood-trading-mcp-url)). Two Vercel lambdas that each decide to refresh will invalidate each other, break the chain, and require a human to re-authenticate — and re-authentication is not a curl command, because "you can only open an agentic account and authenticate your agent on a desktop device" ([finder.com](https://www.finder.com/stock-trading/robinhood-agentic-accounts)). Making this safe demands a single-writer refresher behind a Supabase row or advisory lock, or a cron job that all request paths read from. That is a credential lifecycle the app would now own, replacing one env var.

Layered on top is the protocol tax. MCP over Streamable HTTP is session-oriented: a call is not one HTTP request but `initialize` → `notifications/initialized` → `tools/call`, and a serverless invocation has no warm session to reuse. stdio transport is structurally impossible on Vercel — it requires spawning and holding a child process — which eliminates the whole "npx some-mcp-server" class outright. For a single-user journal with tens of requests a day there is no traffic to keep anything warm, so **every Refresh click is effectively a cold start plus a fresh handshake plus the UUID resolution chain**, in front of a button a human is watching. The irony worth naming is that Anthropic's own 2025 guidance pushes agents *away* from MCP round-trips and toward direct API and code access, reporting a 150,000-token workflow reduced to 2,000 tokens by having the model call underlying APIs in a sandbox rather than through tool calls ([Anthropic Engineering: Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)). A deterministic Next.js route calling Tradier REST with a known endpoint, known parameters and a Zod schema is already the destination of that trajectory. MCP's actual value proposition is N×M integration reduction for a model discovering tools at runtime; this app has N=1 and M=1.

The third objection is security, and it is independent of both. Robinhood's read scope for a connected agent spans **all** accounts — account numbers, balances, positions, transactions, watchlists, scans — not only the separately funded Agentic Account to which *write* scope is confined ([Agentic Trading overview](https://robinhood.com/us/en/support/articles/agentic-trading-overview/)). Robinhood is explicit that it "does not control, supervise, monitor, recommend, or audit these AI agents" and that once data is shared it "leaves Robinhood's security environment." A leaked `TRADIER_API_TOKEN` exposes quotes on a data account. A leaked Robinhood refresh token in a Vercel deployment exposes an entire financial life. For a personal app run by one person, that is a real regression in blast radius, and it is a reason to decline the migration even if every technical obstacle above were solved.

## What Robinhood uniquely supplies is not quotes — it is the account itself

The additive case is strong precisely where Tradier is empty. The MCP surface exposes roughly ninety read tools, among them `get_option_positions`, `get_option_orders`, `get_equity_orders`, `get_realized_pnl`, `get_pnl_trade_history`, `get_portfolio` and `get_equity_tax_lots`. None of that is market data; all of it is the user's actual trading record, and none of it is obtainable from a quotes vendor at any price. Set against the journal's known defects, the fit is obvious: the architecture analysis found that **unrealized P/L does not exist anywhere in the codebase** (`lib/calculations.ts` has zero market-data awareness and an open position contributes exactly 0), that `current_value_cents` is a dead column no code path writes, and that per-leg live prices are fetched and thrown away. Robinhood can answer "what do I actually hold, and what did I actually make" directly — and can do it *in conversation with Claude*, today, with no code written, no token stored in Vercel, and no new identifier format in the repo.

That framing also dissolves most of the objections above. The rotating-refresh-token problem is a serverless-concurrency problem; a single interactive Claude session is a single writer by construction. The handshake latency is irrelevant when a human is asking a question rather than tapping Refresh. The broad read scope is exactly what you *want* for reconciliation, and it stays on the desktop where the OAuth consent happened rather than being persisted into a deployment. The highest-value concrete use is periodic reconciliation: pull `get_option_orders` and `get_pnl_trade_history`, compare against what the journal has recorded, and catch the trades that were entered wrong or never entered at all. A second use is backfilling entry Greeks, which the analysis found **no code path ever populates** (`entry_delta`/`entry_iv` on `legs` are written by nothing, despite `snapshot.perLeg` carrying the values).

One caveat on the positions path. **Whether `get_option_positions` returns Greeks-enriched rows is unresolved.** Both accounts on this login held zero open option positions, so no position object was ever observed; the evidence is indirect, from the tool's own guide naming the available fields as "chain_symbol, type, quantity, average_price, and expiration_date" and instructing callers to "look up strike/option_type via get_option_instruments." If a position object does not even carry the strike, it almost certainly does not carry delta. The likely shape is a join — positions, then `get_option_quotes` on the returned option ids, roughly two calls for a Greeks-enriched table — but that is an inference and should be re-tested once the account holds a position.

## If the real goal is leaving Tradier, the answer is not Robinhood

Worth separating one more proposition that hides inside the question. If the motivation is dissatisfaction with Tradier — the fact that **real-time data requires holding a funded Tradier brokerage account** ("if you are not a Tradier Brokerage account holder, we are unable to provide you with any real-time data solution," [Tradier docs](https://docs.tradier.com/docs/getting-started)), or the hourly ORATS Greeks cadence — then the replacement to evaluate is a data vendor, not a broker's agent interface. **Marketdata.app** is the strongest fit: **free at 100 API credits/day, $12/month billed annually for 10,000/day** ([pricing](https://www.marketdata.app/pricing/), [free plan](https://www.marketdata.app/docs/account/plans/free-forever/)), no brokerage relationship, a plain API token that drops into the existing `app/api/*` + env-var pattern with near-zero code change, and full Greeks plus IV returned in the same call as the quote ([option data API](https://www.marketdata.app/api/options/how-to-use-the-option-data-api/)) — which preserves the current one-call-per-refresh batching shape and, crucially, keeps OCC symbols as the identifier. Its one journal-relevant trap: **Greeks and IV are not stored historically, and any dated request returns null iv/delta/gamma/theta/vega on every plan** ([chain docs](https://www.marketdata.app/docs/api/options/chain/)), so Greeks must be snapshotted into Postgres at fetch time. Alpaca is the runner-up, with Greeks "pre-computed and always included" ([snapshots reference](https://docs.alpaca.markets/us/reference/optionsnapshots)) but only the indicative options feed below **$99/month** ([Alpaca Data](https://alpaca.markets/data)). IBKR and Tastytrade are ruled out on architecture regardless of price — the former needs a locally running TWS/Gateway process, the latter is a dxfeed websocket subscription model, and both reproduce the long-lived-process problem that kills stdio MCP on Vercel.

If the Tradier account stays funded, though, staying put is the cheapest and highest-quality option available: ORATS-sourced Greeks ([Tradier/ORATS](https://production.tradier.com/platforms/orats)) at zero marginal cost, a static bearer token, and native OCC batching.

## Conclusion

The question "can we switch, now that Robinhood has added more capabilities?" turns out to have been aimed at the wrong variable. Robinhood's capability gap closed — the Greeks are there, verified, in one call — and the migration still fails, because what blocks it was never data coverage. It is that Robinhood built an *agent* interface to a *brokerage account*, and this app needs a *data* interface to a *quote feed*. Everything that makes the MCP surface good at the former (OAuth consent scoped to a logged-in human, rotating tokens, broad account read, opaque internal identifiers, model-facing tool descriptions with no versioning contract) is what makes it bad at the latter. The tool's own guide not even mentioning the Greeks it returns is the tell: this surface is documented for a model to read at runtime, not for a compiler to bind against.

The productive reframe is that the journal has two distinct data problems and has been treating them as one. Prices and Greeks for open legs are a commodity purchase — Tradier already solves it, Marketdata.app would solve it for $0–12/month without a brokerage tie, and the actual weaknesses in that path are internal, not vendor-side: no tests on `lib/quotes.ts`, no cache layer, a dead `current_value_cents` column, no unrealized P/L. Fixing those returns more than any vendor swap would. The *account* problem — what was actually filled, at what price, what the realized P&L truly is, whether the journal matches reality — is one Tradier structurally cannot answer and Robinhood answers natively. Connect Robinhood MCP, use it from Claude for reconciliation and exploration, keep the OAuth consent on the desktop where it belongs, and leave the deployed app holding a single static token that can only read quotes.
